1

🧩 Kahneman and the Thinking Fast and Slow framework

Daniel Kahneman proposed that human thinking operates in two modes: System 1 (fast, intuitive, automatic) and System 2 (slow, deliberate, analytical). In robotics, this framework inspires architectures where one reactive module controls movements in real time while another plans at a high level.

✓ When S1/S2 works well

  • Clear separation of responsibilities — planning and control with distinct latencies.
  • Asynchronous buffer — S1 never waits for S2; it continues with the last subgoal.
  • Status feedback — S1 reports progress; S2 replans when needed.
  • Graceful degradation — if S2 fails, S1 maintains safe behavior.

✗ Common pitfalls

  • Synchronous pipeline — making S1 wait for S2 at every frame stalls motor control.
  • Poorly sized frequencies — S2 at 1 Hz with S1 at 200 Hz causes subgoal drift.
  • No watchdog — S2 stuck without a fallback leaves the robot in an undefined state.
  • High-coupling interface — changes in S2 break S1 and vice versa.

Key concepts

Bounded rationality

Make optimal decisions within limited computational resources.

Decision latency

Time between perception and action — critical for closed-loop stability.

Speed-accuracy trade-off

Faster decisions are less accurate; the dual system balances both extremes.

2

🔭 System 2: VLM as a planner at 7–9 Hz

Robotic System 2 uses a Vision-Language Model (VLM) that processes images and natural language to generate high-level action plans. It typically runs at 7–9 Hz because it is computationally expensive, but provides rich semantic understanding of the environment and objectives.

🎯 Why 7–9 Hz is sufficient for planning

High-level planning doesn’t need speed: the task "pick up the cup" changes every second, not every millisecond. The VLM has time to reason about context, language, and visual semantics before issuing a new subgoal.

  • Task decomposition — breaks natural-language instructions into executable subgoals.
  • Subgoal generation — emits embeddings or tokens that S1 interprets as behavioral targets.
  • Adaptive replanning — detects failures via feedback from S1 and generates a new plan.

💡 Practical tip

In practice, the S2 VLM is almost always a pretrained model (Gemini, GPT-4V, InternVL) with minimal fine-tuning for the robotics domain. You rarely train S2 from scratch — the computational cost is prohibitive. The value lies in efficient fine-tuning with demonstration data.

3

⚡ System 1: visuomotor policy at 200 Hz

System 1 is a lightweight neural network — typically a diffusion policy or MLP — which converts visual observations into motor commands at 200+ Hz. It does not "understand" the overall goal; it only executes the motor behavior corresponding to the subgoal received from S2.

⏱️ Why 200 Hz Matters

10 Hz

❌ Insufficient — shaky movements, unable to react to disturbances in real time.

50 Hz

⚠️ Marginal — works for slow tasks; unsuitable for fine manipulation.

200 Hz

✓ Suitable — natural compliance, reaction to disturbances, dexterous manipulation.

1000 Hz

✓ Ideal — impedance control; requires dedicated hardware (FPGA/ASIC).

Key S1 concepts

Action chunking

Predicts action sequences instead of individual actions — reduces jitter and improves smoothness.

Diffusion policy

Models the action distribution through iterative denoising; generates smooth, multimodal trajectories.

Closed-loop control

Continuously adjusts actions based on sensory observations — essential for robustness.

Sensor-actuator latency

Total delay from camera → inference → motor command; it must be <5ms for 200 Hz.

4

🤖 GR00T, Helix, and π0: Real-World Implementations

In 2025–2026, three systems became benchmarks for how the dual-system architecture is implemented in industry. Each solves the problem with a different approach—from modular pipelines to unified models with a dual head.

📊 Design trade-offs

  • Modular (GR00T/Helix) — easier to update S2 without reprocessing S1; higher communication latency.
  • Unified (π0) — shared representations; more efficient; more complex updates.
  • External model (Helix/Gemini) — takes advantage of cutting-edge LLMs without training costs; depends on a stable API.
5

🖥️ Embedded GPU: why no cloud

Autonomous robots need onboard GPUs — such as Jetson Thor or Orin — to run inference locally. Network latency (50–200 ms) makes the cloud unviable for real-time motor control, where every millisecond determines stability and safety.

⚙️ Jetson Thor / Orin

NVIDIA SoC with integrated Ada/Ampere GPU. Thor delivers 2000 sparse TOPS for robotic model inference; Orin, 275 TOPS. Designed for a robot’s thermal envelope (~20–30W).

📉 INT8/INT4 quantization

Reduces FP32 weights to 8 or 4 bits — 4–8x less memory, 2–4x more throughput. Essential for running 7B-parameter VLMs in limited onboard VRAM without critical accuracy loss.

🌡️ Thermal throttling

When the chip heats up, it reduces its clock speed to protect the hardware. On robots, this can degrade inference frequency at critical moments. Proper thermal design is part of the S1/S2 pipeline.

☁️ Selective Offloading

Noncritical tasks (logging, long-term replanning, map updates) can use the cloud with tolerable latency. S1 is always local; S2 can have hybrid components.

💡 Practical sizing rule

For S1 at 200 Hz: the model must take no more than 4 ms per inference. For S2 at 9 Hz: up to 100 ms per inference. This defines the maximum model size without quantization—generally <100M params for S1 and <7B for S2 on Orin.

6

🔗 S1↔S2 orchestration: frequencies and interfaces

Orchestration defines how S1 and S2 communicate: S2 sends subgoals (embeddings or tokens) to S1, which executes and reports status. The challenge is synchronizing a slow pipeline (7 Hz) with a fast one (200 Hz) without bottlenecks — using asynchronous buffers and message prioritization.

✓ Recommended patterns

  • Double buffering — S1 reads from the active buffer while S2 writes to the inactive buffer; no locks.
  • Asynchronous message passing — S2 publishes subgoals to a topic; S1 consumes one in the next cycle.
  • Watchdog timer — if S2 doesn't update for N cycles, S1 enters safe mode.
  • Graceful degradation — S1 keeps the last valid subgoal until S2 recovers.

✗ Anti-patterns

  • Synchronous blocking — S1 waits for S2 every cycle → 100 ms latency instead of 5 ms.
  • High-cost polling — checking S2 every frame consumes CPU that should be used for inference.
  • No failure handling — S2 stuck → S1 has no subgoal → the robot freezes or moves to the default position.
  • Stale subgoal not detected — S1 executes an outdated subgoal without knowing the environment has changed.

🔄 S1↔S2 communication pipeline

1
S2 processes observation

VLM receives frame + instruction → infers plan → serializes subgoal into an embedding.

2
Asynchronous buffer

Subgoal written to the inactive buffer; atomic flag indicates availability to S1.

3
S1 executes

Policy reads the active subgoal → infers an action at 200 Hz → sends torques → reports status.

4
S2 monitors and replans

Receives S1 status → detects failure or progress → decides whether to replan.

✅ Module Summary

✓
Kahneman → robotics — S1/S2 is not a metaphor; it is the architectural separation that resolves the speed vs. intelligence trade-off.
✓
S2 (7–9 Hz) plans, S1 (200 Hz) executes — distinct frequencies, complementary responsibilities; neither can replace the other.
✓
GR00T / Helix / π0 — three real approaches in 2025-2026; modular vs. unified with dual-head is the central design choice.
✓
Asynchronous orchestration — double buffer + watchdog + graceful degradation are the triad that prevents the most common failure points.
